# 实录 Slug 迁移方案（兼容旧数据）

目标：给每篇实录补 `slug`，但不破坏当前 `day` 逻辑，不影响历史内容展示。

## 一、迁移原则

- 不删除旧字段（`day/title/summary/content/tags` 全保留）
- 新增字段必须向后兼容
- 一次性生成 slug 后尽量不再变更，避免旧链接失效

## 二、推荐 slug 规则

建议格式：

- `day-72`
- `w10-weekly-review`

生成优先级：

1. 若 `day` 是数字，优先 `day-{number}`
2. 若 `day` 是周标识（如 `W10`），可用 `week-10-{short-title}`
3. 若发生冲突，追加 `-{n}` 保证唯一

说明：中文标题不建议直接做 slug，优先短英文/拼音化规则，避免编码和复制问题。

## 三、迁移步骤（建议脚本化）

1. 读取 `public/data/journal-entries.json`
2. 遍历每条记录，若无 `slug` 则按规则生成
3. 校验唯一性
4. 输出新 JSON 并备份旧文件
5. 执行 `npm run validate:content`

## 四、兼容读取策略（代码层）

详情页查找顺序建议：

1. 优先按 `slug` 精确匹配
2. 若访问参数形如数字，可回退按 `day` 匹配（兼容历史链接）
3. 仍未命中则显示 404

## 五、风险点与规避

- 风险：slug 重复导致详情页错位  
  规避：迁移脚本中强制唯一校验

- 风险：后续改标题导致 slug 改动  
  规避：slug 一旦生成固定，不随标题变更

- 风险：外部已分享链接失效  
  规避：保留旧 slug 映射表（可选）

## 六、验收标准

- 现有实录全部有唯一 slug
- 列表页与弹窗功能不受影响
- 详情页按 slug 打开内容正确
