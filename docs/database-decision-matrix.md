# 数据库升级决策表（个人网站版）

目标：明确“什么时候该上数据库”，避免过早复杂化，也避免错过升级窗口。

## 一、当前阶段判断

你目前是“内容站 + 个人品牌站”，使用 JSON 数据源是合理的。  
短期优先做内容结构和发布流程，不必立刻上数据库。

## 二、触发条件（命中 3 条即建议升级）

- [ ] 实录总量 > 150 篇
- [ ] 资源总量 > 80 条
- [ ] 每周更新 >= 3 次
- [ ] 需要草稿/发布状态管理
- [ ] 需要多人协作编辑
- [ ] 需要站内搜索（而非简单筛选）
- [ ] 需要按标签/时间/系列做复杂检索
- [ ] 需要后台统计“内容表现”
- [ ] 需要和邮件/私域系统打通
- [ ] 需要历史版本/审计记录

## 三、升级路径（推荐）

### 路径 A：轻量升级（推荐）

- 数据库：PostgreSQL（可用 Supabase 托管）
- 存储：对象存储（OSS）
- 内容管理：先做简易后台，再考虑 CMS

适合你这种个人持续运营站点，学习和维护成本可控。

### 路径 B：继续 JSON（过渡）

- 继续本地 JSON + 脚本
- 补齐 slug、搜索索引、发布流程

仅适合中短期，随着内容量增长维护成本会快速上升。

## 四、成本与收益

不上数据库的收益：

- 架构简单
- 上手快
- 出错面小

不上数据库的代价：

- 内容管理低效
- 协作困难
- 检索和统计能力弱

上数据库的收益：

- 可持续运营能力强
- 支持后台编辑和多维检索
- 易扩展到更多内容形态

上数据库的代价：

- 运维与备份复杂度提升
- 初期开发投入增加

## 五、建议决策

当前建议：继续 JSON 1-3 个月，同时完成以下里程碑：

1. 实录详情页独立路由
2. slug 迁移完成
3. 发布流程标准化（校验 + 检查 + 回滚）
4. 外链和媒体资源稳定化

完成后再复盘一次触发条件，决定是否切换数据库。
